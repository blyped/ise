## Règle : une modification du schéma = une nouvelle migration

**Aucun fichier de ce dossier ne doit jamais être modifié après son application.**

Toute évolution du schéma — table, colonne, contrainte, index, fonction, politique
RLS, donnée de référentiel — passe par la création d'un **nouveau** fichier numéroté
à la suite (`0027_...sql`, `0028_...sql`, …).

Corollaires :

- Éditer une migration déjà appliquée fait diverger le dépôt de la base, et rend
  irreproductible tout environnement reconstruit à partir de zéro.
- Un correctif se fait par une migration corrective, pas par une réécriture de
  l'historique.
- Les migrations doivent rester rejouables : privilégier `create table if not exists`,
  `create or replace function`, `drop policy if exists` avant `create policy`,
  `on conflict do nothing` pour les seeds.
- Un nom de fichier est définitif : il ne se renomme pas.

## Vérification de la ligne de base de sécurité

```sql
select * from private.security_baseline_violations();
```

Cette requête doit renvoyer **0 ligne**. Toute ligne retournée signale une violation à
corriger par une nouvelle migration :

| `kind`                   | Signification                                                                                                                                  |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `rls_disabled`           | Table du schéma `public` sans RLS activée.                                                                                                     |
| `anon_grant`             | Privilège accordé au rôle `anon` sur `public`, `private` ou `analytics`.                                                                       |
| `secdef_no_search_path`  | Fonction `security definer` sans `search_path` figé.                                                                                           |
| `private_exposed`        | Table de `private` ou `analytics` accessible au rôle `authenticated`.                                                                          |
| `private_column_exposed` | Colonne déclarée privée (score de complétion, scores de matching, lien privé d'événement) lisible ou modifiable par `authenticated` ou `anon`. |
| `anon_function_grant`    | Fonction de `public` ou `private` exécutable par `anon` hors de la liste blanche des onze projections public-safe (0061, 0063, 0111).          |

Le contrôle Storage `private.storage_baseline_violations()` doit lui aussi renvoyer **0 ligne** ;
ses huit `kind` sont décrits dans `docs/rls.md` §5.4.

Le contrôle est exécuté par la CI et les tests (MASTER PROMPT §80, §84).

## Note sur l'ordre d'application

Les fichiers sont numérotés selon l'ordre logique de dépendance. Les lots 0007 à 0019
